# 번역표 적용·버전 맞추기(C·D) — 무엇을 하고, 어떻게 돌아가고, 결과는 무엇인가

> B106 데이터/AI 파트 · 2026-11-01 · 대상: 멘토님, 팀원 · 골든테스트 C1~C13, D1~D14, E1~E5 통과 (전체 66개)

---

## 1. 이게 무엇을 하는 프로그램인가

현황표 파서(A)가 뽑은 "설비 한 대 = 한 줄"과 릴리즈노트 파서(B)가 세운 "버전 사다리"를 **연결**하는 프로그램입니다. 연결이 끝나면 설비마다 "어느 릴리즈노트의 몇 번째 칸에 서 있는가"가 정해지고, 거기서부터 적용률·업그레이드 필요 대수·위험 설비가 계산됩니다. 이 프로그램의 핵심 질문인 "기준 버전 N보다 위냐 아래냐"에 답할 수 있게 되는 지점이 바로 여기입니다.

연결은 두 단계로 나뉩니다. 먼저 **번역표 적용(C)** 은 현황표의 설비군 글자(`M-C3(5각) / 통합UI`)를 보고 "이 설비는 어느 릴리즈노트를 봐야 하는가"를 정합니다. 그다음 **버전 맞추기(D)** 는 현황표의 버전 글자(`v3.52_13 (H)`)가 그 릴리즈노트의 어느 칸인지 찾습니다. 둘 다 사람이 결정해야 하는 것은 막지 않고 알려주기만 합니다.

---

## 2. 번역표 적용(C)이 돌아가는 방식

설비군 글자를 받으면 먼저 **번역표**에서 찾습니다. 번역표는 "현황표에 적힌 글자 → 설비군, UI 종류(구UI/통합UI), 구조(Inline/Cluster), 개조 표시(CIP·Prime·C4+)"를 적어둔 27줄짜리 표로, 백엔드에 전달한 `seed_번역표_장소표_v1.sql`의 `model_alias`와 같은 내용입니다. 비교할 때 공백과 대소문자를 무시하므로 `5각\nCluster O2`처럼 줄바꿈이 섞여 있어도 찾습니다. 번역표에 없는 글자(`MC3-INT`)가 오면 "설비군을 지정해 주세요"라는 상태로 돌려주고, 사용자가 검토 화면에서 고른 답은 번역표에 한 줄 추가되어 다음부터는 자동으로 풀립니다.

번역표 한 줄로 안 끝나는 경우가 셋 있습니다. 첫째, `M-C4/C4+ / Smart UI`처럼 글자가 "C4 또는 C4+"로 애매한 경우에는 그 설비의 버전을 봅니다. 버전 끝에 `_DEX`가 있으면 C4+, 없으면 일반 C4로 판정합니다(멘토님 10/29 회신). 둘째, `M-C3`라고만 적혀 UI가 없는 경우에는 통합UI로 봅니다(10/28 확정). 다만 버전이 `v1.1.1…`처럼 구UI 모양이면 구UI로 추정하고 그 사실을 메모에 남깁니다. 셋째, `M-O2/O3`로 적힌 PM 혼합 설비는 설비군이 둘이므로, 버전 라벨(`O3: …`, `O2: …`)마다 따로 설비군을 붙여 양쪽에 1대씩 세게 합니다(10/14·10/21).

설비군이 정해지면 **장소표**로 메모리/파운드리를 정합니다. 장소표는 "사이트·시트·라인 → 메모리/파운드리"를 적어둔 25줄짜리 표(`line_master`)입니다. 평택 S5·V2·P3-S5와 화성 Foundry 시트의 라인은 파운드리, 나머지는 메모리입니다. 화성은 `NRD (MR2동)`이라는 같은 라인명이 Memory 시트와 Foundry 시트에 모두 있으므로 시트 이름까지 봐야 합니다. 장소표보다 우선하는 것이 **설비별 예외**인데, 현황표 파서가 버전 칸의 `메모리버전임` 글자를 보고 붙여준 힌트가 있으면 라인이 파운드리라도 메모리로 봅니다(화성 S1의 C3 2대).

마지막으로 설비군·UI·메모리/파운드리·구조 네 가지를 조합해 **계열(릴리즈노트)** 을 고릅니다. 계열은 14개이고 `version_family`와 같습니다. 개조형(C4+, XMO3, O5 Prime)은 부모 설비군의 릴리즈노트를 쓰고(10/27), C4 DFB와 C4+는 C4 릴리즈노트 안의 `_DFB`·`_DEX` 줄기를 씁니다. O3·O5·KCTC처럼 메모리/파운드리 구분이 없는 계열은 라인이 어디든 같은 릴리즈노트입니다. 아직 파일이 없는 "C3 구UI 파운드리"는 메모리 구UI 릴리즈노트로 대신 비교하고 "확인 중"이라고 표시합니다.

## 3. 버전 맞추기(D)가 돌아가는 방식 — 네 단계

버전 글자를 받으면 먼저 앞뒤 공백과 `(H)`(화성 표시, 버전 정보 아님)만 떼어내고, 릴리즈노트 사다리에서 **글자가 똑같은 칸**을 찾습니다. 있으면 "일치"입니다. 구UI의 `v1.1.1.6B_6 + Hotfix`는 릴리즈노트에 같은 이름의 칸이 있으므로(10/29) 여기서 바로 연결됩니다.

없으면 **표기를 맞춰서** 다시 찾습니다. 소문자로 바꾸고, 공백을 지우고, 밑줄과 대시를 점으로 통일합니다. 그러면 현황표의 `v999.3.7`과 릴리즈노트의 `v999.3_7`이 같아지고(10/20 회신), `V3.53_2`와 `v3.53_2`, `v3.52.F14`와 `v3.52_F14`도 같아집니다. 이때 구분자를 지우지 않고 점으로 "통일"하는 이유가 있습니다. 지워버리면 `v4.56.6.42`와 `v4.56.64.2`가 둘 다 `456642`가 되어 서로 다른 버전이 섞이기 때문입니다. 하나만 맞으면 "표기 보정됨"으로 연결하고 보정 내용을 메모에 남깁니다.

맞는 칸이 **둘 이상**이면 자동으로 고르지 않습니다. 후보를 모두 보여주고 사용자가 고르게 합니다. 릴리즈노트에 `v1.2.3`과 `v1.2_3`이 둘 다 있는 경우처럼 드물지만 생길 수 있는 상황입니다.

하나도 없으면 **미등록**입니다. 미등록일 때 두 가지를 더 해봅니다. 하나는 같은 대분류의 다른 릴리즈노트를 뒤지는 것입니다. `Cluster Ox` 설비의 `v1060`은 Cluster Ox 릴리즈노트에는 없지만 Cluster O2 릴리즈노트에는 있으므로 "이 버전은 Cluster O2 릴리즈노트에만 있어요 — 설비군이 잘못 적힌 것 아닌가요?"라고 제안합니다. 멘토님이 10/29에 확인해 준 화성 16L의 실제 오기 사례가 바로 이것입니다. 연습 데이터를 돌려보니 평택에서도 같은 종류가 두 대 더 나왔습니다(`Ox(inline)` 설비에 Inline O2 버전, `5각 Cluster O2` 설비에 Cluster Ox 버전). 다른 하나는 끝의 꼬리표를 떼어 기본 버전을 찾는 것입니다. `v1.1.1.6B_6_c`는 릴리즈노트에 없지만 `v1.1.1.6B_6`은 있으므로 "기본 버전은 있음 — 그 뒤에 '릴리즈노트에 추가' 가능"이라고 알려줍니다. 멘토님이 10/29에 "릴리즈노트에 없는 핫픽스 버전을 사용자가 입력하게 하라"고 한 것의 구현입니다. 사용자가 추가하면 사다리의 순서 번호(10, 20, 30)의 사이값(예: 65)으로 끼워 넣고, 그 칸에는 "수동 등록"이라는 표시가 남습니다.

버전 칸이 비어 있으면 "누락"이고, 그 계열의 릴리즈노트 파일 자체가 없으면 "릴리즈노트 없음"입니다. 둘 다 에러가 아니라 상태입니다.

## 4. 집계(E)는 어떻게 되나

맞추기가 끝나면 설비마다 "릴리즈노트 X의 Y번째 칸"이 있습니다. 사용자가 기준 버전 N을 정하면, 같은 줄기(기본/DFB/DEX) 안에서 설비 칸이 N 칸보다 위거나 같으면 **적용**, 아래면 **업그레이드 필요**입니다(10/14 확정: N 이상이면 적용). 미등록과 누락은 **전체 대수에는 들어가되 업그레이드 필요에는 들어가지 않고** 따로 셉니다(10/28 이의 없음). 그래서 적용률의 분모는 미등록·누락을 포함하고, 분자는 적용만입니다. HPA는 전체 대수에서 아예 빠집니다. PM 혼합 설비는 버전마다 1대로 세어 O2 쪽과 O3 쪽에 각각 들어갑니다.

연습 데이터로 N을 "각 릴리즈노트의 최신 칸"으로 두고 돌려보면, 평택 O2(메모리)는 41대 중 12대 적용으로 29.3%, 화성 KCTC Cluster O2는 8대 중 7대로 87.5% 같은 숫자가 나옵니다. 이 숫자 계산은 전부 코드가 하고 AI는 관여하지 않습니다.

## 5. 결과 파일

`demo_match.py`를 돌리면 `*_매칭결과.csv`가 나옵니다. 설비 한 대(PM 혼합은 버전 하나)가 한 줄이고 열은 다음과 같습니다: 사이트, 시트, 라인, 설비호기, 설비군(원문), 설비군, 메모리/파운드리, 릴리즈노트, PM, 버전(원문), **연결된 칸**, 순서, **상태**(일치 / 표기 보정 / 후보 여러 개 / 미등록 / 누락 / 릴리즈노트 없음), **설명**(사람이 읽는 문장), 원본. 화면에는 "연결됨 228대, 집계 제외 5대, 미등록 3대"처럼 요약이 뜨고 확인 필요한 설비만 한 줄씩 다시 나옵니다. JSON은 백엔드가 `equipment_version`(`release_version_id`, `match_status`)에 넣을 모양입니다.

```
python demo_match.py 평택설비현황표_교육용_2026-10-05.xlsx 화성_설비현황표_SEMES_ETCH_교육용_2026-10-05.xlsx --release <릴리즈노트 폴더> --mentor <멘토 원본 폴더> --out parsed_match
python -m pytest tests -q          # 66 passed
```

## 6. 확인한 것

번역표: UI 미표기 M-C3 → 통합UI, 5각·6각 무시, 메모리버전임 예외, C4/C4+ 버전 판정(두 방향), CIP·Prime·KCTC 네 표기, 파운드리 라인의 O2, 새 표기 → 확인 필요, HPA 제외, 같은 라인명 두 시트. 버전 맞추기: 일치, (H) 제거, 공백, 대소문자, 점·밑줄, 접미사 구분자, `+ Hotfix`, 미등록 핫픽스 → 추가 제안, 미등록 일반, 설비군 오기 후보, 누락, DFB 줄기, 후보 여럿, 수동 등록 후 일치. 집계: N 이상 적용, 분모 처리, PM 혼합 양쪽, HPA 제외. 실데이터: 평택 236대·화성 132대 전부 설비군이 풀리고, 미등록은 각 3대(전부 의도한 함정)입니다.

## 7. 다음 단계와의 연결

여기까지가 "엑셀 → 설비 → 어느 릴리즈노트 몇 번째 칸 → 적용률"의 데이터 흐름 전부입니다. 백엔드는 이 결과를 DB에 넣고(가져오기 → 검토 → 저장), 프론트는 `상태`와 `설명` 열을 검토 화면에 그대로 보여주면 됩니다. 남은 데이터/AI 작업은 AI 세 가지(열 매핑, 자연어→조회 조건, 보고서)와 예측 검증이며, 모두 이 결과 위에서 돌아갑니다.
