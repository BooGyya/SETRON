# 테스트 전략

개발 단계에서 무엇을 어떤 방법으로 검증할지 정합니다. 기능별 완료 기준의 원본은 팀 기능 및 요구사항 명세서의 `백엔드 작업표`(완료 확인 방법 열)이며, 이 문서는 그 기준을 테스트 종류별로 나누고 실행·기록 방법을 정합니다.

## 1. 테스트 종류와 범위

| 종류 | 무엇을 확인하나 | 실행 방법 | 외부 연동 |
| --- | --- | --- | --- |
| 단위 테스트 | 업무 규칙, 계산, 형식 해석, 오류 처리 | `pytest` 자동 실행 | 쓰지 않음. Excel·DB·AI는 가짜 객체로 대신함 |
| 통합 테스트 | 실제 연동에서만 드러나는 동작: Excel COM 연결, MySQL 저장·롤백·제약조건, 회사 AI 호출 | 사람이 환경을 준비해 실행하고 결과를 기록 | 실제 Excel, 로컬 MySQL, 회사 AI API |
| 데이터 검증 | 이상치가 들어간 테스트 데이터로 버전 해석·검증 규칙이 문제를 모두 찾는지 | 테스트 데이터를 가져와 결과 확인 | 테스트 데이터 (Jira S15P31B106-15, 40) |
| AI 추출 정확도 | AI가 양식별 Excel에서 값을 맞게 추출하는지 | 정답 데이터와 비교해 정확도 계산 | 회사 AI API, 평가셋 (Jira S15P31B106-71) |
| 화면 확인 | 화면 표시, 이동, 사용자 입력 흐름 | 사람이 앱을 실행해 확인 | 앱 전체 |

- 업무 규칙은 단위 테스트로 먼저 확인합니다. 통합 테스트는 실제 연동에서만 확인할 수 있는 동작으로 범위를 좁힙니다.
- 단위 테스트는 Excel, MySQL, 회사 AI가 없는 PC에서도 통과해야 합니다.
- AI 추출의 합격 기준(필드별 일치율 등)은 Jira S15P31B106-71에서 정한 기준을 따릅니다.
- MySQL 통합 테스트는 Docker의 전용 MySQL 5.6.19에서 자동 실행합니다. 실제 사용 PC의 Windows MySQL 접속·저장 검증은 해당 환경이 준비된 뒤 별도로 진행합니다.

BE-007의 GMS 실제 호출과 전체 필드 평가는 [AI Excel 추출 테스트 결과](test-results/be-007-ai-extraction.md)에 기록합니다. 원본 셀로 먼저 고정한 135개 레코드·16개 필드와 같은 지시문으로 `gpt-6.1-sol`·`gpt-6-luna`를 비교했습니다. 후처리 일치율은 sol 99.36%, luna 90.10%(추가 결과 페널티 포함)이며, 같은 정답 위치만 비교하면 luna 91.52%입니다. 판정 보류 131개를 제외한 커버리지는 93.94%로 같고, 모델별·시트별 1회 측정입니다. [sol 원본·정답·실제 응답](test-results/be-007-evaluation/README.md), [luna 응답·토큰·시간](test-results/be-007-evaluation-luna/README.md), [모델별 추출 오류 비교표](test-results/be-007-evaluation-luna/model-field-errors.md)와 재계산 스크립트를 보존합니다.

BE-006·BE-007 병합 후 연결 점검(2026-11-02): 두 커밋과 BE-006 원본 파일의 보존은 확인했으나, 가져오기 화면이 `read_sheet()`에 필수 `app_pid`·`full_name`을 전달하지 않는 호환성 오류를 발견했습니다. 실제 함수 시그니처를 강제한 Qt 테스트로 기존 실패 4건을 재현한 뒤 선택 키를 파일명·프로세스·전체 경로로 바꾸고 데모의 호출 계약도 맞췄습니다. 동명 파일의 다른 경로·다른 창 구분과 목록 순서 변경 후 선택 유지를 포함해 `test_ui_import.py`, `test_excel_reader.py`, `test_extraction_service.py`, `test_openai_client.py`, `test_ai_service.py`, `test_excel_import_service.py`의 **236개가 통과**했습니다. [선택 상태 화면](screenshots/b2/import-workbook-identity.png)은 합성 자료이며, 실제 읽기 확인은 기존 교육용 Excel의 Memory·Foundry에서 별도로 수행했습니다. 두 시트가 보관 스냅샷과 같았고 BE-007에 보관 응답을 `EXAMPLE`로 재생해 85개·50개 행을 확인했습니다. 추가 실제 AI 호출과 원본 수정·저장은 없었습니다.

### 공통 UI 검증 (작업 단위 2)

`tests/test_ui_common.py`는 Qt offscreen 플랫폼에서 실제 위젯과 QTest 이벤트로 시작 안내, 준비 중 메뉴, 담당 페이지 등록·이동, 단일 활성 메뉴, 원본 아이콘·폰트 로딩, 키보드 조작과 페이지 입력 상태 보존을 확인합니다. 1600×960·1100×800·960×600 창에서 헤더 줄바꿈·사이드바 스크롤과, 긴 페이지를 숨겼을 때 다른 화면이 늘어나지 않는지도 검증합니다. 업무 화면이나 DB·Excel은 실행하지 않습니다.

```powershell
uv run --locked python -m pytest tests/test_ui_common.py -q
uv run --locked python -m setron --auto-close-ms 1500
```

별도로 Windows 네이티브 실행과 VER3 Light 대비 실제 Qt 렌더링을 확인합니다. 로컬 Qt 테스트는 GitLab 파이프라인 실행이나 실데이터 통합 테스트를 의미하지 않습니다.

### 공통 조회 조건 검증 (작업 단위 3)

`tests/test_ui_query.py`는 초안/적용 분리, 전체와 미지정 구분, Site→Fab→Line 종속 선택, 잘못된 부모 관계 거부, 적용 스냅샷 불변성, 선택지 교체와 이전 요청 무효화를 검증합니다. Fab·Line 관계는 테스트 전용이며 회사 데이터로 간주하지 않습니다.

실제 Qt 위젯으로 콤보박스와 빠른 선택 버튼 동기화, 적용 시에만 발생하는 신호, 초기화 후 기존 적용 조건 보존, 메뉴 이동 후 상태 보존, 페이지별 패널 표시 여부, 키보드 적용과 1600×960·1100×800·960×600 배치를 확인합니다. 기본 VER3 미리보기 선택지와 테스트용 선택지를 모두 검사하며 DB·Excel은 호출하지 않습니다.

```powershell
uv run --locked python -m pytest tests/test_ui_common.py tests/test_ui_query.py -q
```

수동 확인: Site/설비군 선택 → 조회 적용 → 선택 변경 → 기존 적용 문구 유지 및 재적용 필요 표시 → 전체 조건으로 → 다시 적용 순서로 확인합니다. 선택지 미리보기와 DB 미연결 안내가 표시되어야 하며, 조건 적용을 데이터 조회 완료로 표시하지 않아야 합니다. 공통 패널 단독에서는 목표 버튼이 비활성화되며 앱의 7번 연결에서 활성화합니다. 개인 기본 선택지 설정은 비활성화 상태입니다.

### 대시보드 검증 (작업 단위 4)

`tests/test_ui_dashboard.py`는 테스트 전용 자료를 주입해 기존 집계 서비스의 물리 대수·설비/계열 건수·HPA 제외·복수 SW/PM·판단 불가 결과를 확인합니다. 정규 위치와 원본 구역을 구분하고 Fab 미지정/알려진 Line, UI 설비군/모델/버전 계열의 별도 매핑을 검증합니다. 위험 후보와 N 미달은 독립적으로 확인합니다.

Qt 조작으로 최초 미적용, 적용 후 일괄 갱신, 초안 변경 후 결과 보존, 표/차트/수치표 일치, 범례 표시 전환, 빈 결과·실패·재시도, HPA만 있는 범위, 이전 응답 거부, 선택지 교체 시 무효화와 메뉴 복귀 후 상태 보존을 확인합니다. 일반 셀과 위험 후보의 정확한 전달 ID가 다르며, 추이의 관측 공백을 연결하거나 0%로 채우지 않는지도 검증합니다.

```powershell
uv run --locked python -m pytest tests/test_ui_dashboard.py -q
uv run --locked python -m setron --auto-close-ms 1500
```

별도로 실제 Qt 렌더링을 VER3의 KPI·표·구성비·막대·추이와 비교합니다. 1600×960·1100×800·960×600에서 메인 가로 넘침 없이 지표/범례가 재배치되고, 넓은 현황표와 수치표만 내부 스크롤하는지 확인합니다. 도넛은 실제 면적이 있는 슬라이스로 표시해야 하며 원본 아이콘은 자연 크기를 유지합니다. 화면·테스트 수치 모두 합성/테스트 자료이며 DB 통합 검증 결과가 아닙니다.

### 버전 히트맵 검증 (작업 단위 5)

`tests/test_ui_heatmap.py`는 한 번 계산한 동일 스냅샷을 대시보드·히트맵이 공유하는지 확인합니다. 정규 Site/Fab/Line/설비군 범위, 한 호기 한 타일, 복수 SW/PM과 불일치, 문자열 순서와 다른 릴리즈 순서의 N-k, 목표 달성과 위험의 독립, 위험 미확인·SW 미등록·HPA 분석 제외를 테스트 전용 자료로 검증합니다.

Qt 이벤트로 밀집/버전 전환, 후보 필터 후 전체 복귀, 변하지 않는 적용 범위/요약, 빈 결과·실패·재시도, 이전 요청/선택지 세대 거부, 메뉴 복귀 상태 보존, 키보드 선택과 후속 요청 ID를 확인합니다. 1600×960·1100×800·960×600에서 두 보기의 메인 가로 넘침·타일 범위·ID 잘림과 원본 아이콘 크기도 검사합니다.

```powershell
uv run --locked python -m pytest tests/test_ui_heatmap.py tests/test_ui_dashboard.py -q
```

별도로 합성 예시 63대의 두 보기를 실제 Qt로 렌더링해 VER3의 Site별 타일·보기 버튼·요약 배치와 비교합니다. 타일은 목표 색상을 유지하며 후보만 빨간 테두리/기호를 추가해야 합니다. 좁은 창에서 열을 줄이고 요약을 아래로 보내며 긴 PM 원문이 타일 밖으로 넘지 않는지 확인합니다. 실제 DB/Excel 연동이나 후속 상세 화면을 검증한 것은 아닙니다.

### 설비 목록·상세 검증 (작업 단위 6)

`tests/test_ui_equipment.py`는 선택 SW/설비 전체 판정 분리, 같은 기준일 원문 보존, 전달 ID 부분집합·중복/위험/이전 요청 검사와 표시 필터의 범위 보존을 검증합니다. 정규 Fab·Line을 원본 구역에서 추정하지 않으며 SW 미등록·HPA·미입력·복수 SW/PM도 확인합니다.

실제 Qt 이벤트로 헤더 → 목록, 대시보드 셀/후보 → 서로 다른 목록, 히트맵 타일 → 상세, Enter 행 선택, 이전 조회 복귀, 12대 페이지와 검색/상태/후보/정렬을 확인합니다. 상세 복귀 시 목록 필터·페이지와 히트맵 보기/선택이 유지되어야 하며 재적용·선택지 변경·실패 시 이전 상세가 남지 않아야 합니다. 긴 원문은 DisplayRole/ToolTipRole에서 그대로 제공해야 합니다.

```powershell
uv run --locked python -m pytest tests/test_ui_equipment.py -q
```

1600×960·1100×800·960×600 목록/상세에서 메인 가로 넘침 없이 표 내부만 가로 스크롤하는지 확인하고 별도로 Qt 렌더링을 VER3와 비교합니다. 위험 근거/원본 셀은 미연결 안내가 있어야 하며 PM별 위험을 추정하지 않아야 합니다. 합성 데이터 화면 검증이며 DB·Excel·관측 이력·정정/저장·목표 편집 검증은 아닙니다.

### 목표 N 편집 검증 (작업 단위 7)

`tests/test_ui_targets.py`는 모델/계열별 불변 목표 계약, 초안/적용 분리, 중복/잘못된 ID 거부, 같은 계열의 확인된 릴리즈와 Hotfix만 새 목표로 허용하는지 검증합니다. UI 설비군이 같아도 모델별 N은 독립적이며, 순서 미확인/중복과 릴리즈 ID 중복은 선택 불가여야 합니다. 명시적 목표 미지정·기존 잘못된 목표·없는 계열·빈 선택지에서는 정상 목표를 만들어내지 않습니다.

Qt 이벤트로 버튼 진입·키보드 선택·다중 목표 편집·원래 초안 복원·완료/취소/Esc/닫기·동일 대화상자 재사용을 검사합니다. 완료는 목표 초안 신호만 보내며 조회 적용 뒤에 대시보드·추이·히트맵·목록·전체 상세가 같은 N으로 바뀌어야 합니다. 이후 초안이 기존 상세/범위 요약에 섞이거나 공급자 기본 N·위험 결과를 수정해서는 안 됩니다. 편집 중 자료 변경·오래된 요청·계산 실패/재시도·새 창 초기화와 긴 원문 보존도 확인합니다.

```powershell
uv run --locked python -m pytest tests/test_ui_targets.py -q
```

1600×960·1100×800·960×600에서 대화상자와 공통 패널의 가로 넘침·일반 텍스트 렌더링·선택 버튼을 검증하고, 별도로 VER3의 선택 버튼/현재 기준 표시와 실제 Qt 렌더링을 비교합니다. 작은 창의 선택 목록/변경 요약은 내부 세로 스크롤을 사용합니다. 실제 DB 저장·전사/사용자별 정책·실데이터 통합 검증은 아닙니다.

### 버전 목록·상세 검증 (B-1)

## 2. 단위 테스트 작성 규칙

- 테스트 파일은 `tests/test_<대상 모듈>.py`로 만듭니다. 예: `tests/test_excel_reader.py`, `tests/test_ai_service.py`
- 실제 Excel·DB·AI를 호출하지 않습니다. 외부 연동은 다음처럼 바꿔 끼웁니다.

  | 대상 | 바꾸는 방법 | 예 |
  | --- | --- | --- |
  | Excel (xlwings) | `monkeypatch`로 모듈의 `xw`를 가짜 객체로 교체 | `tests/test_excel_reader.py`의 `use_fake_excel` |
  | 회사 AI | `ExampleChatClient`에 정상·실패 응답을 넣어 서비스에 전달 | `tests/test_ai_service.py` |
  | DB | 서비스가 받는 Repository 형식을 따르는 메모리 저장소를 테스트에서 만들어 전달 | Repository 구현 시 추가 |

DB 연결·트랜잭션의 단위 테스트는 SQLite 메모리 DB에서 실제 SQL을 실행합니다. MySQL 5.6.19의 SQL·자료형·잠금 동작은 아래 통합 테스트에서 확인합니다.

- 테스트 하나는 한 가지 상황을 확인합니다. 함수 이름은 상황과 기대 결과를 영어로, 테스트 설명(docstring, `ids`)은 한국어로 씁니다.
- 명세의 예시 수치는 그대로 테스트 값으로 씁니다. 예: 혼합 설비 O2는 N 미만·O3는 N 이상 → 실제 1대, 적용률 50%
- 정상 동작뿐 아니라 명세의 오류·예외 처리(빈 값, 판단 불가, 연결 실패 등)도 테스트합니다.

스키마는 프로젝트의 `database/schema_mysql5619.sql`을 테스트 파일 위치를 기준으로 찾으므로 별도 경로 설정이 필요하지 않습니다. 기존 관리 테이블이 없는 테스트 DB에 스키마를 적용하고 이번 검증에서 만든 테이블만 삭제합니다. 접속 설정이 없으면 실제 MySQL 테스트를 건너뛰며, 설정했는데 연결이나 권한에 문제가 있으면 실패로 보고합니다.

DB 회귀 테스트는 저장 성공·전체 취소, JSON·원문 보존, 삭제 전 위험 근거 보존과 동시 삭제를 검증합니다. 실제 연결 중단은 저장 도중과 COMMIT 전송 직전에 테스트 연결만 종료해 검증하며, 성공한 commit의 응답만 유실되는 경우는 포함하지 않습니다. 자세한 접속·오류 처리 기준은 [README](../README.md#db-연결과-저장-처리-be-001)를 참고합니다.
