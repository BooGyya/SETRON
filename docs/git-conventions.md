# Git Conventions

## 브랜치 운영

`develop`에서 개발 작업을 통합하고, 릴리스할 범위가 준비되면 GitLab의 Merge Request(MR)로 `master`에 병합합니다. 원격 저장소의 기본 브랜치는 `master`이며, 개발 작업의 기준 브랜치는 `develop`입니다. 작업 브랜치에서 변경한 뒤 MR로 검토하고, `develop`과 `master`에 직접 커밋하거나 push하지 않습니다.

| 브랜치 | 용도 | 예시 |
| --- | --- | --- |
| `master` | 검증을 마친 릴리스 코드 유지 | `master` |
| `develop` | 다음 릴리스를 위한 개발 작업 통합 | `develop` |
| `feature/*` | 새로운 기능 | `feature/equipment-list` |
| `fix/*` | 오류 수정 | `fix/excel-validation` |
| `docs/*` | 문서 작성 및 수정 | `docs/project-architecture` |
| `chore/*` | 초기 설정과 의존성 관리 | `chore/project-setup` |

브랜치 이름은 영문 소문자와 하이픈으로 작업 내용을 짧게 표현합니다. 서로 관련 없는 작업은 브랜치를 나눕니다.

`master`와 `develop`은 계속 유지합니다. 별도의 `release/*` 브랜치는 만들지 않고 `develop → master` MR로 릴리스를 진행합니다.

## 작업 흐름

1. `git fetch origin`으로 원격 상태를 갱신하고, 최신 `origin/develop`을 기준으로 작업 브랜치를 만듭니다.
2. 변경 범위에 맞게 동작과 테스트를 확인합니다. 문서나 초기 설정만 바꾼 경우에는 링크, 파일 경로, 설정 구문 등 해당 변경에 필요한 항목을 확인합니다.
3. 하나의 목적을 가진 변경 단위로 커밋합니다.
4. `git push -u origin <작업 브랜치>`로 작업 브랜치를 원격 저장소에 올립니다. 이후에는 같은 브랜치에 변경을 추가하고 push합니다.
5. `develop`을 대상으로 MR을 작성합니다. 구현이 끝나지 않았다면 Draft로 표시합니다.
6. 리뷰 의견을 반영하고 충돌을 해결합니다. 코드가 바뀌면 필요한 검증을 다시 수행합니다.
7. MR의 병합 성공과 원격 `develop`에 변경이 반영된 것을 확인합니다.
8. 로컬 `develop`을 갱신한 뒤, 사용한 작업 브랜치를 로컬과 원격 저장소에서 모두 삭제합니다. 병합 전에는 작업 브랜치를 삭제하지 않습니다.

## 릴리스 흐름

1. `master` 이후 `develop`에 쌓인 변경 전체가 릴리스 가능한지 확인하고, 해당 범위의 동작과 테스트를 검증합니다.
2. 소스 브랜치를 `develop`, 대상 브랜치를 `master`로 지정해 릴리스 MR을 작성합니다. 본문에 포함 기능과 수정 사항, 검증 결과를 정리합니다.
3. 릴리스 MR에서는 Squash commits와 소스 브랜치 삭제를 끕니다. 커밋 이력을 유지하는 merge commit 방식으로 병합합니다.
4. 리뷰와 검증을 마친 뒤 `master` 병합 권한이 있는 계정에서 MR을 병합합니다. 현재 `master`는 보호된 브랜치입니다.
5. 병합 성공과 `master`의 변경 반영을 확인하고 로컬 브랜치를 갱신합니다. `develop`은 다음 개발을 위해 유지합니다.

최종 검증 후 `develop`에 새 변경이 추가되면 갱신된 소스 커밋을 기준으로 다시 검증합니다. `master`에만 있는 수정 사항이 생기면 `master → develop` MR로 개발 브랜치에도 반영합니다. 릴리스 MR은 포함할 변경이 모두 준비되었을 때 작성하며, 초기 구조 설정만으로 바로 릴리스하지 않습니다.

## 커밋 메시지

Conventional Commits 형식을 사용합니다. type은 영문 소문자로 쓰고, 설명은 한국어로 간결하게 작성합니다.

```text
type: 변경 내용
type(scope): 변경 내용
```

`scope`는 선택 사항입니다. 필요한 경우 `ui`, `equipment`, `version`, `excel` 등 변경 영역을 적습니다.

| type | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 새로운 기능 추가 | `feat(equipment): 설비 목록 조회 추가` |
| `fix` | 오류 수정 | `fix(excel): 빈 셀 검증 오류 수정` |
| `docs` | 문서 작성 및 수정 | `docs: 폴더 아키텍처 문서 추가` |
| `refactor` | 동작을 유지한 코드 구조 개선 | `refactor(version): 상대 버전 계산 로직 분리` |
| `test` | 테스트 추가 및 수정 | `test(version): 상대 버전 계산 테스트 추가` |
| `chore` | 설정 및 의존성 관리 | `chore: 프로젝트 초기 설정 추가` |
| `style` | 동작에 영향을 주지 않는 서식 변경 | `style: import 정렬 및 들여쓰기 정리` |

추가 설명이 필요하면 제목 아래 한 줄을 비우고 변경 이유와 영향을 본문에 적습니다. 호환성을 깨는 변경은 type 또는 scope 뒤에 `!`를 붙이거나 `BREAKING CHANGE:` 푸터로 표시합니다.

## MR 작성과 병합

MR은 하나의 목적을 가진 변경 단위로 작성합니다. 리뷰어가 이전 대화나 작업 과정을 몰라도 변경 이유와 결과를 이해할 수 있도록 설명합니다. 서로 독립적으로 검토하고 병합할 수 있는 작업은 별도의 MR로 분리합니다.

### 작성

일반 작업 MR의 대상은 `develop`, 릴리스 MR의 대상은 `master`로 지정합니다. 제목은 커밋 메시지와 같은 형식을 사용하며, 작업 중 작성한 커밋을 나열하기보다 최종 변경 내용을 요약합니다.

```text
feat(equipment): 설비 목록 조회 기능 추가
```

본문에는 다음 내용을 작성합니다.

| 항목 | 작성 내용 |
| --- | --- |
| 변경 배경 | 해결하려는 문제와 변경이 필요한 이유 |
| 주요 변경 사항 | 추가·수정한 동작과 영향을 받는 기능 또는 모듈 |
| 검증 결과 | 확인한 동작, 테스트 방법과 결과. 확인하지 못한 항목이 있으면 사유도 기재 |
| 관련 자료 | 관련 이슈 링크. 화면이 바뀌면 변경 내용을 확인할 수 있는 스크린샷 첨부 |

### 리뷰

변경한 모듈을 이해하는 팀원에게 리뷰를 요청하고, 팀원 1명 이상의 리뷰를 받은 뒤 병합하는 방식을 권장합니다.

리뷰에서는 변경 목적에 맞게 동작하는지, 모듈 간 책임을 지키는지, 예외 상황과 필요한 검증을 다뤘는지 확인합니다. 리뷰 의견은 코드에 반영하거나 반영하지 않은 이유를 설명하고, 추가 논의가 필요한 내용은 병합 전에 합의합니다.

리뷰 이후 동작이나 영향 범위가 달라지면 MR 본문과 검증 결과도 갱신합니다.

### 병합

병합 전에는 리뷰 의견 처리 여부, 대상 브랜치와의 충돌 여부, 변경 범위에 필요한 검증 결과를 확인합니다. 자동 검사가 구성되어 있다면 검사 결과도 확인합니다. 충돌을 해결하면서 코드가 바뀐 경우에는 영향을 받는 동작을 다시 검증합니다.

일반 작업 브랜치를 `develop`에 병합할 때는 Squash commits 사용을 권장합니다. 변경을 하나의 커밋으로 정리하고, 최종 커밋 메시지는 커밋 규칙에 맞춰 작성합니다. GitLab 프로젝트의 병합 설정에 따라 별도의 merge commit이 추가될 수 있습니다. 병합 성공과 변경 반영을 확인한 뒤 로컬과 원격 작업 브랜치를 모두 삭제합니다.

`develop → master` 릴리스 MR과 `master → develop` 동기화 MR에서는 Squash commits를 사용하지 않습니다. 두 브랜치는 장기 유지하므로 원래 커밋 이력을 보존하고, 병합 후에도 삭제하지 않습니다.

## 규칙 변경

브랜치 전략, 커밋 형식, 리뷰 또는 병합 방식을 바꿀 때는 이 문서를 함께 수정하고 팀에 공유합니다.
