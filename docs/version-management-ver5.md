## 실제 저장과 작업본의 경계

- **기존 설치 SW 정정**은 명시적으로 전달된 `ManagementGateway`가 있을 때 기존 저장 서비스를 호출한다. 같은 설비·실제 관측일·고정 PM/일반 SW 위치를 확인하고, 조회 당시 값이 달라졌으면 재조회를 요청한다. 사용자의 두 단계 검토·최종 저장 확인 전에는 저장하지 않는다. 리비전 충돌 검사는 기존 서비스가 수행한다.
- 성공은 `ManagementResult`일 때만 확정하고 기존 공통 저장 후 갱신 신호를 재사용한다. 확정 실패는 입력 유지·다시 시도, 알 수 없는 결과는 재저장 금지로 구분한다. 저장 중 창 닫기와 중복 제출을 차단한다. 공급자가 없으면 명확히 표시한 세션 작업본만 저장한다.
- **릴리즈 등록/수정, Item의 분류·JIRA·비고·적용 범위 편집, 설비 정보 등록/수정/삭제 검토, 보관 생성**은 이번 프론트 범위에서 현재 앱 세션의 독립 작업본이다. 화면에 DB 저장과 구분해 표시하며 앱을 닫으면 없어질 수 있다. 기존 릴리즈 관리 서비스로 이동하는 레거시 `open_editor()` 경로는 보존한다. 실제 신규 등록·보관 영속화 정책/API는 새로 만들지 않는다.
- 작업본의 버전 원문을 정규화하거나 다른 계열과 합치지 않는다. 순서를 입력하면 확인 근거가 필요하고, 출시일 미기재는 허용한다. Item 포함 판정은 기존 누적 적용 읽기 서비스를 재사용하며 다른 릴리즈의 명시 연결 상태를 덮어쓰지 않는다.
- 설비 정보 작업본은 실제 설비·PM·SW·관측 기록을 삭제/생성하지 않는다. 전 사업장 호기 중복과 필수 사유를 검사하고 대상별 입력을 유지한다. 삭제 버튼은 **삭제 검토 요청**이며 실제 삭제가 아니다.
- 보관본은 **현재 세션에서 저장한 변경 묶음의 불변 사본**이다. 전체 현황 스냅샷·DB 과거 이력으로 표시하지 않는다. 비교도 작업 A/B의 변경값만 비교한다. 확인 이후 변경이 생기면 보관 범위를 재검토해야 한다.
- 가져오기 성공 신호로 받은 입력 작업 번호·파일/시트·행 수·저장 위치는 이력의 **저장 요약**으로 남긴다. 제공되지 않은 행별 전후 차이를 추정하지 않는다.
- 선택 작업 Excel은 확인한 보관 작업만 출력하고 원문·처리 근거 포함 여부를 반영한다. 선택 후 데이터가 바뀌어도 출력 범위는 고정한다. 셀 원문을 수식으로 실행하지 않는다. DB 전체 SQL은 기존 별도 내보내기 경로이며 SQL 가져오기·병합·복원 기능은 추가하지 않는다.
- 버전 비교·경과 기간 설정은 이 화면 안에서만 적용한다. 공통 목표 N·위험 규칙·릴리즈 순서·원본·실제 장비 SW를 변경하지 않는다. 과거 관측 없는 날짜는 다른 날짜로 대체하지 않는다.

## 프론트 확인 순서

1. 다섯 탭을 차례로 눌러 위치·선택 밑줄 확인. 상단 좌우 화살표·공통 뒤로 버튼이 없고, 상세의 목록 복귀·입력 취소는 동작하는지 확인.
2. 설치 버전에서 실제 저장 관측일로 조회 → 타일이 아닌 표의 버전 정정 → SW 대상을 바꿔 입력 유지·취소·전후 비교 확인.
3. 릴리즈 목록에서 모델/계열·검색·페이지·초기화·상세 → 새 등록/수정의 필수 사유·중복 원문·날짜·순서 근거 검사 확인.
4. 상세의 Item 선택·추가/수정 → 분류·내용·상태·범위·JIRA·비고·사유 확인. 최신 자료로 바뀐 뒤 오래된 입력은 반영하지 않음.
5. 설비 정보의 수정/등록/삭제 검토 → 작업본 저장 → 변경 검토 → 체크 전 보관 불가 → 보관 생성 → 내용/비교/근거 확인.
6. 선택 작업 Excel의 범위·파일명·근거 포함·취소·완료/실패 확인. DB 전체 SQL과 구분.
7. 버전 비교의 Relative/Actual·계열·목표·기간 설정과 데이터 없음/미확인 상태 확인.
