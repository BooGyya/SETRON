# BE-007 AI Excel 추출 테스트 결과

2026-11-02에 GMS의 `gpt-6.1-sol`과 `gpt-6-luna`로 화성 교육용 Excel의 `Memory`와 `Foundry` 시트를 추출했다. 원본 셀로 먼저 고정한 **135개 결과 행·16개 필드의 같은 정답표**로 비교했다. 이번 측정에서 luna는 sol보다 시간이 18.22%, 전체 토큰이 20.77% 적었지만, 현재 추출 계약과 후처리 기준의 일치율은 낮았다.

| 핵심 지표 | gpt-6.1-sol | gpt-6-luna |
| --- | ---: | ---: |
| AI 원문 계약 일치율 | 99.58% | 93.43% |
| 후처리 일치율, 추가 결과 페널티 포함 | 99.36% (2,016/2,029) | 90.10% (1,857/2,061) |
| 같은 정답 위치만의 후처리 일치율 | 99.36% (2,016/2,029) | 91.52% (1,857/2,029) |
| 후처리 값 있는 정답 일치율 | 98.42% | 86.06% |
| 전체 토큰 | 26,779 | 21,217 |
| 시간 합계 | 128.643초 | 105.199초 |

정답 위치 2,160개 중 판정 보류 131개를 제외한 커버리지는 두 모델 모두 93.94%다. luna의 추가 페널티 32개는 후처리에서 PM 대응에 실패한 두 결과에 적용됐다. 표기 차이·실제 필드 배정 오류·후처리 차단을 구분한 해석은 10절에 기록했다. 모델별·시트별 1회 측정이며 일반적인 모델 성능으로 확대하지 않는다.

1~8절은 최초 부분 검사와 당시 수정 이력, **9절은 sol 전체 필드 평가, 10절은 luna와의 비교**다. [sol 증거](be-007-evaluation/README.md)와 [luna 응답·모델별 오류 비교표](be-007-evaluation-luna/README.md)를 구분해 보관했다. 기존 부분 검사에서 확인하지 않았던 CIP·Prime 관련 오류도 전체 필드 평가에 포함했다.

이 결과는 설비 현황표 한 파일의 두 시트에 한정된다. 릴리즈 노트, 다른 Excel 양식, 사내 AI 서버의 정확도는 이번 실제 호출 범위에 포함하지 않았다.

## 2. 입력과 출력 크기

입력 길이는 시스템 지시문과 셀 자료를 포함한 메시지 본문의 문자 수다. HTTP 요청 전체의 바이트 크기나 입력 토큰 수는 아니다. 출력 길이는 AI가 반환한 응답 본문 문자열의 문자 수다.

| 항목 | Memory | Foundry |
| --- | ---: | ---: |
| 읽은 원본 범위 | A2:V91 | A2:U57 |
| 읽은 행 수 | 90 | 56 |
| 읽은 열 수 | 22 | 21 |
| 값이 있는 셀 수 | 374 | 173 |
| 병합 범위 수 | 21 | 18 |
| 입력 메시지 길이 | 6,500자 | 4,164자 |
| 출력 응답 길이 | 40,523자 | 28,911자 |
| 원본 호기 셀 수 | 85 | 47 |
| 후처리 결과 행 수 | 85 | 50 |

Foundry의 혼합형 한 호기를 PM 4개로 펼쳐 3개 행이 추가됐다. 따라서 47개 원본 호기 셀에서 50개 결과 행이 나온 것은 호기가 추가 생성된 결과가 아니다. 두 시트의 호기 수 합계 132개는 시트별 원본 셀을 합산한 수치이며, 두 시트를 통합한 물리 설비의 중복 제거 대수는 계산하지 않았다.

최초 호출에서는 토큰 사용량, 사용 크레딧, 금액을 수집하지 않았다. 9절의 재평가에서는 실제 응답의 토큰 사용량을 수집했다. 문자 수로 토큰이나 비용을 환산하지 않는다.

## 3. 실제 호출 이력과 소요 시간

| 순서 | 요청 | 시간 제한 | 결과 | 측정 시간 |
| --- | --- | ---: | --- | ---: |
| 1 | 짧은 연결 확인 요청 | 60초 | 실제 응답 `OK` 수신 | 1.63초 |
| 2 | Memory 전체 추출 | 60초 | `AITimeoutError`, 결과 `FAILED` | 60.26초 |

- 성공한 두 시트의 측정 시간 합계: **133.75초**.
- 연결 확인과 실패 요청을 포함한 네 요청의 측정 시간 합계: **195.64초**.

측정 구간은 클라이언트 생성부터 호출·응답 처리와 검토 자료 생성까지다. 사용자 응답 대기, 코드 수정, 회귀 테스트 시간은 위 합계에 포함하지 않았다. 각 시트의 성공 결과는 1회 측정값이며 평균이나 최대 응답 시간으로 일반화하지 않는다.

SDK 자동 재시도는 꺼진 상태다. Memory의 두 번째 요청은 첫 요청의 시간 초과를 확인한 뒤 명시적으로 실행했다. 180초는 검증 실행에서만 적용했으며 `.env`의 60초 설정은 유지했다. 이 모델로 전체 시트를 처리할 때는 60초보다 긴 제한이 필요하다는 점이 확인됐다.

## 4. 원본과 대조한 방법

AI가 제시한 `sources`의 주소만 검사하면 다른 행의 정상 셀을 잘못 연결한 경우를 놓칠 수 있다. 이번에는 원본의 호기 열과 SW 열을 기준으로 결과를 별도로 대조했다.

| 확인 항목 | 원본 기준과 대조 방법 |
| --- | --- |
| 호기와 원본 위치 | Memory E열, Foundry D열의 데이터 셀을 결과의 호기 값·출처 주소와 비교. 원본에만 있는 셀과 결과에만 있는 셀도 확인 |
| 일반 행의 SW 대응 | 호기 원본 행 번호를 기준으로 Memory H열, Foundry G열을 찾아 결과의 `version_raw`와 비교 |
| 혼합형의 PM별 SW | Foundry C57·G57·P57의 모델·버전·PM 관계와 펼쳐진 4개 결과를 비교 |
| C3 UI | Memory D열, Foundry C열에서 `구UI` 또는 `통합UI`가 명시된 행만 골라 `LEGACY`·`INTEGRATED`와 비교 |
| 재생 시 원본 일관성 | 코드 수정 후 같은 시트를 다시 읽고, 최초 성공 호출에 사용한 셀 스냅샷과 모든 값이 같은지 확인 |

아래 지표의 일치율은 `일치 또는 대조 통과 건수 ÷ 대조 대상 건수 × 100`이다. 서로 다른 평가 단위를 더해 전체 정확도로 계산하지 않는다.

| 평가 항목 | Memory | Foundry | 합계 | 일치율 |
| --- | ---: | ---: | ---: | ---: |
| 호기 값과 원본 셀 위치 | 85/85 | 47/47 | 132/132 | 100% |
| 일반 행의 SW 원문 대응 | 85/85 | 46/46 | 131/131 | 100% |
| 혼합형 PM·모델·SW 대응, 수정 후 재생 | 해당 없음 | 4/4 | 4/4 | 100% |
| 명시된 C3 UI | 22/22 | 15/15 | 37/37 | 100% |

호기 대조에서는 누락 셀과 추가 셀이 모두 0개였다. 일반 행의 SW 대조에는 원본 공란을 `None`으로 유지한 경우와 `메모리버전임` 같은 메모 문자열을 보존한 경우도 포함한다. 따라서 131/131은 **원본과의 대응 일치율**이며, 유효한 버전 번호만의 정답률이나 업무상 적용 적합률은 아니다.

## 5. 입력과 후처리 결과 예시

### Memory의 C3 구UI

원본 셀 일부는 다음과 같다.

| 셀 | 원본 값 |
| --- | --- |
| D5 | `M-C3 (구UI)` |
| E5 | `ESPE11` |
| H5 | `v1.1.1.6B_6_c` |

검토 자료에서는 모델명 `M-C3`, 호기 `ESPE11`, UI `LEGACY`, SW `v1.1.1.6B_6_c`로 정리됐다. 호기 출처는 E5, SW 출처는 H5, 모델·UI 출처는 D5로 유지됐다. 원본 셀에 없는 기준일과 사업장 값은 생성하지 않았다.

### Foundry의 혼합형

| 셀 | 원본 값 |
| --- | --- |
| C57 | `M-O2/O3` |
| D57 | `ESON81` |
| G57 | `O3: v4.50.1.1_a / O2: v3.53_F2` |
| P57 | `PM1, 2는 O3, PM3, 4는 O2` |

수정 후 실제 응답 재생으로 확인한 결과는 다음과 같다.

| 호기 | PM | 모델 | SW 버전 | SW 원본 위치 |
| --- | --- | --- | --- | --- |
| ESON81 | PM1 | M-O3 | `v4.50.1.1_a` | G57 |
| ESON81 | PM2 | M-O3 | `v4.50.1.1_a` | G57 |
| ESON81 | PM3 | M-O2 | `v3.53_F2` | G57 |
| ESON81 | PM4 | M-O2 | `v3.53_F2` | G57 |

AI는 원문 표기 제약에 맞춰 일부 PM 이름을 `2`, `4`, 일부 모델명을 `O3`로 반환했다. 후처리는 P57의 명시적인 PM 목록과 C57의 공유 접두사를 근거로 `PM2`, `PM4`, `M-O3`를 복원했다. AI 반환 원문과 원본 셀 전체 값은 별도로 유지했다.

## 6. 발견한 코드 오류와 수정 검증

기존 원본 대조 규칙은 `version_raw`가 원본 셀 전체와 같거나, 끝의 출시일만 분리한 경우를 허용했다. 이 때문에 G57에 함께 적힌 두 버전에서 올바르게 분리한 값도 원본 불일치로 처리했다. 최초 Foundry 결과에서는 혼합형 4개 행의 SW 값이 후처리에서 차단됐다.

수정한 내용은 다음과 같다.

1. `O3: 버전 / O2: 버전`에서 해당 모델에 명시된 **완전한 버전 값**만 허용했다. 접미사를 잘라낸 값, 다른 계열의 버전, 중복 계열 표기, Engine 값 대체는 계속 거부한다.
2. `PM1, 2`처럼 원본에 명시된 목록에서만 축약 PM 번호를 고정 위치 이름으로 정리했다. `PM12`에서 `PM1`을 잘못 뽑은 경우는 거부한다.
3. 원본이 `M-O2/O3`처럼 접두사를 공유한 경우에만 `O3`를 `M-O3`로 복원했다. 단독 `O3`를 일괄 별칭으로 처리하지 않는다.

수정 후에는 이미 받은 두 실제 응답을 `ExampleChatClient`로 재생했다. 이 단계는 추가 API 호출 0회이며, 새로운 모델 추론 결과가 아니다. 재생에 사용한 원문 응답은 실제 GMS 응답이고, 재생 전송 계층의 구분값은 `EXAMPLE`이다. 원본 스냅샷 일치와 혼합형 4개 대응을 다시 확인했으며, 두 시트 모두 원본 값 대조에서 거부된 항목은 0개였다.

관련 회귀 테스트는 다음 명령으로 실행해 **172개가 통과**했다. 이 수치는 Python 코드 회귀 테스트의 통과 건수이며 모델 정확도의 평가 분모가 아니다.

## 7. 남은 검토 항목

아래는 수정 후 실제 응답 재생 결과의 검토 사유 수다. 같은 행에 여러 필드 안내가 붙고 시트 전체 안내도 포함되므로, 잘못 추출한 호기 수나 AI 오답 수로 해석하지 않는다.

| 검토 사유의 필드 | Memory | Foundry |
| --- | ---: | ---: |
| 기준 날짜 | 86 | 51 |
| 사업장 | 86 | 35 |
| 버전 계열 | 64 | 35 |

주요 확인 사항은 다음과 같다.

- 기준 날짜와 일부 사업장 값이 시트에 없어 확정하지 않았다. Memory의 사업장은 파일명만으로 채우지 않았다.
- 버전 계열 대응이 미확정인 결과가 남아 있다. 원문 보존과 DB 계열 확정은 구분해서 확인해야 한다.
- Memory에서는 원본 설비군 표기와 알려진 모델 소속이 다른 26건을 검토 대상으로 표시했다.
- Foundry의 `Smart UI` 표기 12건은 현재 UI 정규화 규칙에 매핑되지 않아 검토 안내가 발생했다.
- `메모리버전임` 같은 메모와 비어 있는 SW 값은 원문대로 보존했다. 실제 버전 확인과 저장 전 검증이 필요하다.

`AIStatus.OK`는 응답을 받아 검토 자료를 생성했다는 뜻이다. 필수값 보완과 BE-008 검증을 거치지 않은 이번 결과를 저장 가능한 자료로 판정하지 않는다.

## 8. 최초 부분 평가의 해석과 증거 보존 범위

최초 검사에서 확인한 결론은 **호기·SW 원본 대응·명시된 C3 UI의 부분 일치율 100%**였다. 다음은 그 시점의 한계이며, 전체 필드 평가와 영구 증거 보존은 9절에서 보완했다.

1. 대조 대상은 설비 현황표 한 파일의 두 시트뿐이다. 릴리즈 노트와 다른 양식의 일반화 성능은 측정하지 않았다.
2. 기준일, 사업장, 라인, 분류, 모델, 생산 영역, PM, 계열, UI, 형상, 개조 정보 등 전체 공통 필드에 대해 검토자가 확정한 정답표가 없다.
3. 원본 누락, 적절한 `null`, 판정 보류, AI의 잘못된 추출, 백엔드 정규화 오류를 전체 필드 단위로 분류·집계하지 않았다.
4. 기록한 일치율은 AI 응답과 백엔드 후처리를 거친 결과다. AI 단독 성능과 후처리 후 성능을 별도로 측정하지 않았다.
5. 실행마다 한 번의 성공 결과를 확인했으므로 반복 호출에 따른 변동도 측정하지 않았다.

최초 실행의 원본 셀 스냅샷과 실제 응답은 OS 임시 파일에 저장해 대조·재생에 사용한 뒤 정리했다. 1~8절의 수치는 해당 실행의 도구 출력 기록을 근거로 보존한 것이다. 최초 원문 응답 JSON을 복원할 수는 없으며, 9절의 재호출 응답은 최초 응답과 구분해서 보관한다.

합격 기준은 [테스트 전략](../testing.md)의 AI 추출 평가 기준과 연결해 확정한다. 아래 측정값만으로 미확정된 업무 기준의 합격을 선언하지 않는다.

## 9. 원본 정답표를 이용한 전체 필드 재평가

### 평가 기준과 입력 고정

사용자가 확인한 기준은 **원본 셀 기준으로 평가하고 확정된 정규화 규칙만 적용**하는 것이다. 파일명에서 사업장을, 시트명에서 생산 영역을 채우지 않았다. 열린 Excel의 셀 값·좌표·병합 범위를 13:31:08 KST에 보관했고, 정답표를 2026-11-02 13:42:16 KST에 고정했다. 실제 요청은 이후 13:44~13:46에 수행했다. 요청 후 정답값과 정책을 변경하지 않았다.

- 원본 호기 셀 132개: Memory 85개, Foundry 47개.
- 혼합형 ESON81을 PM1~PM4로 펼친 정답 레코드: Memory 85개, Foundry 50개, 합계 135개.
- 각 단계의 필드 위치: 135 × 16 = 2,160개. 원문과 후처리 두 단계를 합친 대조표는 4,320개 필드 행이다.
- 원문 정답: 값 있음 802개, 원본 누락에 따른 `null` 1,358개.
- 후처리 정답: 값 있음 825개, 원본 누락에 따른 `null` 1,204개, 판정 보류 131개. 평가 가능 커버리지는 2,029/2,160 = 93.94%다.

정답은 제품의 정규화 함수를 호출하지 않는 독립적인 원본 규칙으로 작성했다. 실제 병합 범위만 공유하고 병합되지 않은 공란은 앞 행으로 채우지 않았다. 별도 DB 계열을 확정할 수 없는 93개, Smart UI 대응 12개, 원본 설비군과 알려진 모델 소속이 충돌하는 26개를 보류했다. 보류 항목도 정답표와 대조표에 넣고 실제 반환값을 보존한다. 이번에는 131개 모두 후처리 결과가 `null`이었다.

원문 단계는 연속 부분 문자열과 필드 분리 방식까지 고정한 **엄격한 추출 계약 일치율**이다. 표기가 다르지만 후처리로 같은 의미가 되는 경우도 원문 불일치에 포함한다. 후처리 단계는 확정된 표준값과 비교한다. 원본 누락의 `null`은 채점하지만 판정 보류는 값 정확도 분모에서 제외한다. 레코드가 누락되면 `null` 정답도 실패로 처리하며, 추가 레코드는 16개 필드 모두 오류로 더한다.

정답표는 [원본 기반 평가 정책](be-007-evaluation/reference-policy.md)에 따른 규칙 기반 기준이며 업무 전문가의 최종 검수 완료를 뜻하지 않는다. 특히 CIP·Prime 주석의 필드 분리 기준을 정책에 명시했다. 모델·개조 정보의 업무 정의를 바꾸면 새 정책으로 별도 평가해야 한다.

## 10. gpt-6-luna와 gpt-6.1-sol 동일 조건 비교

### 비교 조건

sol의 영구 보관 응답을 기준선으로 사용하고 luna의 실제 API 요청 2회만 추가했다. luna는 2026-11-02 13:53~13:55 KST에 호출했다. 두 모델의 시트별 시스템·사용자 메시지를 문자열 단위로 비교해 완전히 같은 것을 확인했다. 다음 항목도 일치했다.

- 셀·병합 스냅샷, 정답표, 평가 정책, 수집·평가 스크립트의 SHA-256.
- 추출·정규화·AI 어댑터 등 제품 파일별 SHA-256, `openai 3.42.1`, GMS 주소.
- 시간 제한 180초, 자동 재시도 0회, `model`·`messages`만 보내는 Chat Completions 경로.

모델명만 luna 실행 프로세스에서 지정했다. `.env`, 원본 Excel, 제품 코드는 수정하지 않았고, 기존 sol 묶음의 20개 파일도 해시가 그대로 유지됐다. 정답을 다시 만들거나 두 응답을 보고 정책을 바꾸지 않았다. `temperature`·`seed`·추론 노력은 양쪽 모두 명시하지 않아 서버의 모델별 기본값이 적용된다.

추가 페널티를 제외하고 **같은 확정 정답 위치 2,029개만 비교**하면 sol 2,016개(99.36%), luna 1,857개(91.52%)가 일치한다. 이때도 대응에 실패한 기대 PM 필드는 실패로 유지한다. 차이는 7.84%p이며, 추가 페널티 포함 주 지표의 차이는 9.26%p다.

### 어떤 값이 달랐는가

[모델별 전체 오류 비교표](be-007-evaluation-luna/model-field-errors.md)에는 한 모델 이상 불일치한 모든 정답 필드에 대해 **정답·sol 실제 값·luna 실제 값·판정·원본 셀**을 나란히 기록했다. 대응되지 않은 실제 행의 필드도 별도 표와 JSON에 남겼다. 대표 사례는 다음과 같다.

| 원본과 필드 | 정답 | sol | luna | 해석 |
| --- | --- | --- | --- | --- |
| Memory D5, model_name | `M-C3` | `M-C3` | `M-C3 (구UI)` | luna가 모델의 UI 주석을 분리하지 못함. 동일 유형 C3 모델 22개에서 발생 |
| Memory D4, structure_type | `null` | `null` | `M-C3` | 모델명을 구조 구분으로 잘못 배정. 이런 잘못된 채움 37개와 Inline·Cluster 누락 48개가 원문 구조 필드에서 발생 |
| Memory D5, family_name | 후처리 `C3` | `C3` | `null` | luna의 주석 포함 모델명으로 인해 후처리가 C3 모델을 인식하지 못함. 계열 22개 누락 |
| Foundry B4 등, site | `기흥` | `기흥` | `(기흥)` | 위치를 찾았지만 괄호를 남겨 확정 표기와 불일치. 22개 발생하며 잘못된 사업장 추정과는 다름 |
| Foundry B55·B56, line | `null` | `null` | `MFAB`, 출처 B54 | 병합되지 않은 공란을 앞 행의 값으로 채운 실제 대응 오류 2개 |
| Foundry C57, PM1·PM2의 model_name | 원문 `O3`, 후처리 `M-O3` | 원문 `O3` → 후처리 `M-O3` | 원문 `M-O3` → 후처리 `null` | luna의 값은 PM 설명과 의미가 맞지만 C57의 연속 부분 문자열이 아니어서 원본 대조에서 차단 |

혼합형의 luna 원문 PM·모델·SW 연결은 의미상 맞는 부분이 있지만, 현재 계약은 프로그램이 정규화하도록 원문 부분 문자열을 요구한다. 따라서 원문 지표는 엄격한 계약 위반으로, 후처리 지표는 실제 검토 자료의 손실로 각각 반영했다. 후처리 손실 전체를 모델의 의미 이해 오류로 부르지 않는다. 이번 비교 중 제품 코드를 수정하지 않아 이러한 차단도 기준선에 그대로 남겼다.

같은 정답 위치로 나란히 비교하면 원문은 둘 다 일치 2,016개, sol만 일치 135개, luna만 일치 2개, 둘 다 불일치 7개다. 후처리는 둘 다 일치 1,857개, sol만 일치 159개, luna만 일치 0개, 둘 다 불일치 13개이며 보류 131개가 별도다. 추가 결과 페널티 32개는 이 짝 비교에 섞지 않고 따로 기록했다.

현재 계약과 제품 코드에서는 sol의 일치율이 높고 luna의 시간·토큰이 적었다. 구조 필드의 배정 오류, 사업장 괄호 처리, 모델 주석 분리와 혼합형 원문 대조 차단은 서로 다른 원인이다. 시트별 한 번의 결과이므로 모델의 일반적인 우열이나 반복 안정성을 확정하지 않는다.
